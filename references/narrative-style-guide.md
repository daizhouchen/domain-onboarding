# 叙事内化写作规范 · Narrative Style Guide

> **框架是思考工具，不是写作模板。分析结果应该内化到叙事中。**
> ——继承自 prism-research 的设计哲学

> **中文是默认语言。英文出现必须有理由。**
> ——v1.4 / v1.5 整合后的语言宪法

这是 v0.2 的灵魂文档。method-internalization 管"哪些词不能出现在正文里"（黑名单），这一份管"正文应该长什么样子"（正面规范）。

读者打开 HTML，看到的应该是一份**可以一气呵成读完的连贯叙事**——而不是一份用 H3 切成"事实层 / 机制层 / 观点层"的分析报告。分析框架在你脑子里跑完之后，**留在纸上的只有故事和判断**。

文档分为四部分：

- **第一部分：语言宪法**——读叙事示范之前先把语言规则刻进去，避免被英文示例污染。
- **第二部分：叙事内化**——分析结构 ≠ 写作结构的核心命题、段落 lead、事实嵌入、机制段、观点反例。
- **第三部分：结构组织**——v0.3 学习规律强化清单（路线图段、过渡桥、分组归类、跨域同构、命门评分、章末总结、判断式 lead）。
- **第四部分：领域特异性**——玩家地图、三尺度时间、结构/范式叙事化、跨域同构、known unknowns、章节衔接、末尾自检。

# 第一部分：语言宪法（中英文混用三层规则）

> 起因：用户反馈"给我中文产物但中间莫名其妙夹杂很多英文，很突然，给人拽洋文的感觉"。
> 后续观察发现，单靠"首次注释一次"还不够——已通行中译的术语在第二次、第三次出现时如果仍写英文，整篇读下来还是中英拼贴感。
> 这一部分定下三层落地规则——**中文为主语言，英文出现必须有理由、必须有注释，且通行中译必须直接用中文**。

## 1.1 三层强制规则

写中文产物时，每一个英文词都要在脑子里跑一遍三层规则：

```
┌─────────────────────────────────────────────────────────────┐
│  第 1 层（最强约束）：通行中译必用中文                       │
│  ────────────────────────────────────────                   │
│  汉语世界已通行的中译——直接用中文，全文中文，无需英文括号。 │
│  例：凯恩斯 / 布雷顿森林 / 美联储 / 哈佛 / 彭博               │
│  即使首次出现，也只是"可选"加一次英文括号；后续必须全部中文。 │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  第 2 层（中等约束）：圈内必要英文 + 首次注释                │
│  ────────────────────────────────────────                   │
│  圈内中文文献也直接用英文的术语——保留英文，首次必加中文释义。│
│  例：HNSW / RAG / IMF / SWIFT / SDK                         │
│  首次出现："HNSW（分层可导航小世界图）"；后续直接 HNSW。     │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  第 3 层（最严约束）：英文虚词禁止                           │
│  ────────────────────────────────────────                   │
│  by / with / like / etc. / via / per 等英文虚词——一律改中文。│
│  这些词没有"圈内必要"，纯属拽洋文。                          │
└─────────────────────────────────────────────────────────────┘
```

## 1.2 首次出现的标准模板

英文术语首次出现按下面三个模板挑一个用，**后续重复出现遵循 1.1 的三层规则**。

**模板 A · 英文（中文释义）** —— 适用于：圈内必要英文、没有通行中译的圈内黑话。

```
HNSW（分层可导航小世界图）
RAG（检索增强生成）
ANN（近似最近邻）
SaaS（软件即服务）
RTGS（实时全额结算）
ColBERT / 后期交互（late interaction）
```

**模板 B · 中文（英文）** —— 适用于：已经有通行中译、写中文更自然的术语。

```
特里芬难题（Triffin Dilemma）
离岸美元（Eurodollar）
量化宽松（QE）
布雷顿森林（Bretton Woods）
代理行（correspondent banking）
召回率（recall）
交叉编码器（cross-encoder）
```

> 注：第 1.1 层的"通行中译必用中文"——首次也只是可选加英文括号，第二次起必须裸中文。

**模板 C · 英文（一句话身份）** —— 适用于：人名 / 公司名带身份说明。

```
Edo Liberty（Pinecone CEO，前 AWS SageMaker 工程师）
Andrew Kane（pgvector 维护者，加拿大独立开发者）
佐尔坦 · 波萨尔（Zoltan Pozsar，前瑞信全球策略师，"布雷顿森林 III"论点提出者）
```

## 1.5 英文虚词禁用清单 + 中文替换

下面这些英文虚词、连接词、短语在中文产物里**一律禁用**——必须改成中文表达。
这些词没有"圈内必要"理由，纯属拽洋文。

| 禁用 | 中文替换 |
|------|---------|
| `by` | 由 / 通过 / 经 |
| `with` | 与 / 和 / 加 / 配 / 带着 |
| `like` / `such as` | 比如 / 例如 / 像 / 譬如 |
| `vs.` / `vs` | 对比 / 还是 / 或 / 和 |
| `a.k.a.` / `aka` | 即 / 又称 / 也叫 / 也就是 |
| `etc.` | 等 / 等等 / 之类 |
| `i.e.` | 即 / 也就是 |
| `e.g.` | 例如 / 比如 |
| `via` | 经由 / 通过 |
| `per` | 按 / 每 |
| `re:` | 关于 / 就 …… 而言 |
| `world's central bank` | 世界央行 |
| `central bank`（句子主语位置） | 央行 |
| `central banks` | 各国央行 |
| `amateur`（作普通名词） | 外行 |
| `incumbent`（作名词） | 在位者 |
| `swap line` | 互换额度（首次可加 swap line） |
| `ground truth` | 真实信号（首次可加 ground truth） |
| `however` | 但是 / 不过 / 然而（首选不用"然而"） |
| `furthermore` | 而且 / 进一步 |
| `therefore` | 所以 / 因此 |
| `in addition` | 此外 / 另外 |

> 关键差异：第 1.4 层的圈内英文是"圈内人都说英文"——保留它有身份识别价值；第 1.5 层的虚词是"中文有完全等价的表达，没人非要说英文"——纯属习惯性拽洋文。

## 1.6 决策树：3 步分流

碰到一个英文词，**按下面三步分流**——回答前一个问题就直接落地，不用走完三步。

```
拿到一个英文术语，问 3 个问题：

────────────────────────────────────────────────────────────
Q1. 这个词的中文译法已通行吗？
   （"通行" = 高校教科书 + 中文媒体常用 + 学术圈共识）
────────────────────────────────────────────────────────────
  是 → 直接用中文（首次出现可选加英文括号；后续必须全中文）
       例：凯恩斯 / 布雷顿森林 / 美联储 / 哈佛 / 彭博
  否 → 进入 Q2

────────────────────────────────────────────────────────────
Q2. 这个词在圈内是否必要？（圈内人都说英文）
────────────────────────────────────────────────────────────
  是 → 用英文为主，但首次出现必加中文括号注释
       例：HNSW（分层可导航小世界图） / RAG（检索增强生成） / SWIFT（环球银行金融电信协会）
  否 → 进入 Q3

────────────────────────────────────────────────────────────
Q3. 这个词是否人名 / 公司名 / 产品名 / 论文标题？
────────────────────────────────────────────────────────────
  人名 → 知名 + 中译通行 → 用中文（凯恩斯）
         不知名 → 模板 C：英文 + 一句话身份（Edo Liberty（Pinecone CEO））
  公司/产品 → 通行的（如英伟达、彭博）用中文，否则保留英文 + 首次注释
  论文标题 → 中文译名 + 英文原标题括号《主导货币范式》（Dominant Currency Paradigm）
  都不是 → 不要用，改用中文表达——这个词大概率属于第 1.5 节虚词禁用清单
```

## 1.7 自检 5 问 + grep 扫描方法

### 1.7.1 写完一段，回头读一遍，问 5 个问题

任何一个答 yes 就要改：

1. 这段读起来流畅吗？英文是不是打断了节奏？
2. 第一次出现的英文术语都加了括号注释吗？
3. 已经在第 1.3 节"通行中译总表"里出现的词，我是不是还在写英文？
4. 圈外读者能不能读懂？还是只对圈内人友好？
5. 整段英文字符占比是否 > 30%（quote 引用除外）？

### 1.7.2 全章 grep 扫描三道检查

每章写完后跑下面三道扫描：

1. **专有名词扫描**：`grep -oE '[A-Z][a-z]+' chapter.html | sort | uniq -c` —— 看高频词，
   超过 3 次的英文专有名词必须有中文译名（首次出现）。
2. **首字母大写词扫描**：`grep -oE '[A-Z]{2,}' chapter.html | sort | uniq -c` ——
   缩写未注释的，回去加注释。
3. **中英密度**：跑 `python3 scripts/render.py` 看 stderr 输出的 `chinese_pct`——
   总体 ≥ 75%（金融类）/ ≥ 65%（技术圈类）。

### 1.7.3 烂例与改进对照（7 组）

**烂例 1**（technical 段落英文堆砌）：

> Pinecone 由 Edo Liberty 创立，他是 ex-AWS SageMaker engineer，更早 at Yahoo Research 做 similarity search……

**改进**：

> Pinecone 由 Edo Liberty（Pinecone CEO）创立——他从 AWS SageMaker 团队出来，更早在 Yahoo 研究院做相似度搜索研究。

---

**烂例 2**（金融段落术语未注释）：

> 60 年代美元贬值压力来自 Triffin Dilemma：要给世界提供 liquidity 就必须 deficit，但 deficit 多了 confidence 就崩。

**改进**：

> 60 年代美元贬值压力来自特里芬难题（Triffin Dilemma）：要给世界提供流动性就得长期赤字，但赤字一多，外界对美元的信心就崩。

---

**烂例 3**（圈内黑话糊脸）：

> 这就是经典的 disruption from below——the incumbent 主动 ignore 低端市场。

**改进**：

> 这就是经典的低端颠覆（disruption from below）——领先者主动忽略低端市场。

**烂例 4**（人名+职位拽洋文 + 连接词偷懒）：

### 1.7.4 给 sample 改的优先级

如果是给已有 sample 补注释（不重写章节），优先级为：

1. **第 9 章（学习路径）**：清单页人名 / 论文 / 数据源最密——必先做
2. **第 4 章（圈内黑话）**：黑话密度最高，最突兀
3. **第 3 章（玩家地图）**：人名 / 公司名首次出现处
4. **第 5 章（结构层）**：抽象英文术语多
5. **第 7 章（别处的故事）**：跨产品对照，公司名密度高

每个术语只改第一次出现的位置；后续出现按 1.1 三层规则处理。
不要动 mechanism / viewpoint / chapter-summary / quote / cite 块的内部结构。
不要破坏 fact-ref 锚点（`<sup><a id="fact-N">[N]</a></sup>`）。
不要动 quote 引用（除非整句英文需要中译）。

# 第二部分：叙事内化（思考结构 ≠ 写作结构）

## 2.1 核心命题

### 2.1.1 两套结构的分离

```
       思考时用的结构（你脑子里跑）              写出来给读者看的样子（HTML 上的样子）
       ─────────────────────────                 ─────────────────────────────────
       事件层（发生了什么）                      连贯叙事（一段一段读下去）
       机制层（怎么运转）           ──────►      段落里嵌脚注 [1][2][3]
       结构层（不可压缩约束）                    机制段落用 <p class="mechanism">
       范式层（处于哪种范式）                    观点段落用 <blockquote class="viewpoint">
       反身性 / 跨域同构                         class 不可见，但闸门能扫
```

读者看到的是**"它怎么走到今天"**，不是**"事实层 / 机制层 / 观点层"**。
class 是给质量闸门看的钩子，**不是给读者看的标题**。

### 2.1.2 v0.1 vs v0.2 对比

```diff
v0.1（暴露分析框架，读起来像分析报告）：

  <h2>三层证据链 · 事实 → 机制 → 观点</h2>

  <h3>事实层</h3>
  <ul>
    <li id="fact-1">Pinecone 2023-04 完成 B 轮 1 亿美元（来源：Crunchbase）</li>
    <li id="fact-2">pgvector 2023-07 发布 0.5 支持 HNSW（来源：GitHub release）</li>
    <li id="fact-3">Supabase 2024 Q1 财报把 pgvector 列为主推（来源：Supabase 博客）</li>
  </ul>

  <h3>机制层</h3>
  <p>向量数据库护城河来自数据规模 × 查询质量飞轮，引用 fact[1][2][3]……</p>

  <h3>观点层</h3>
  <p>纯向量库 5 年内被消解。反例：Pinecone 估值在涨。证伪条件：……</p>


v0.2（叙事化呈现，分析内化进段落）：

  <h2>它怎么走到今天</h2>

  <p>2021 年还要专门部署、专门调优——那时是定制活
     <sup><a id="fact-1" class="fact-ref" href="#fact-data-1">[1]</a></sup>。
     2023 年 7 月 pgvector 0.5 装上 HNSW
     <sup><a id="fact-2" class="fact-ref" href="#fact-data-2">[2]</a></sup>，
     一年后 Supabase 直接把它当主推卖点
     <sup><a id="fact-3" class="fact-ref" href="#fact-data-3">[3]</a></sup>——
     向量检索从"专业活"变成"装个插件"，整个赛道的进入门槛在两年里塌了一格。</p>

  <p class="mechanism" data-fact-refs="f1,f2,f3">
     这件事的力学其实简单：每当一个新品类还需要专门部署、专门运维、专门 SDK，
     就给老 DB 厂商留出"功能下沉"的窗口期——只要插件做出来、性能够 80% 用户用，
     新品类的"非必要性"就开始扩散。pgvector 的崛起不是技术胜利，是窗口期被准时利用。</p>

  <blockquote class="viewpoint">
     纯向量库作为独立品类，3 年内会被压缩到 20% 的超大规模场景。
     <span class="counter">但是反过来——如果 OpenAI / Anthropic 把 vector store 嵌进 API 一并送，
     那连 Pinecone 那一层 RAG 编排平台也立不住，整个独立赛道全军覆没。</span>
  </blockquote>
```

差距一眼能看到：v0.1 是分析报告，v0.2 是文章。读者读 v0.2 时，**根本不需要知道你用了"事实层/机制层/观点层"这套**——故事自己讲清楚了。

## 2.2 段落 lead 句规范

### 2.2.1 规则

**每段第一句必须独立成立**——读者只读这一句也能掌握这段的核心。
段落剩下的部分是"展开 + 证据 + 反例"，但 lead 句是判断，不是过渡。

为什么？因为读者会扫读。一份领域速通三千字，没人逐字读——读者扫每段第一句，挑感兴趣的段落细读。lead 句撑不住，整段就废了。

### 2.2.2 五个好的 lead 句示范

| # | Lead 句 | 为什么好 |
|---|---------|---------|
| 1 | "向量数据库这个赛道在 2024 年悄悄做完了一件事：算法白菜化，决胜搬到工程和生态。" | 一句话给出 thesis，有时间、有判断、有视角切换 |
| 2 | "Pinecone 的真正麻烦不是 pgvector 性能追上来——是它没有理由继续存在。" | 反共识判断，挑战主流叙事，钩子很硬 |
| 3 | "如果 2026 年还存在估值 10 亿美元的纯向量库公司，本文判断错。" | 给出可证伪条件，读者立刻知道你在赌什么 |
| 4 | "这一切其实在 2010 年代的 NoSQL 赛道演过一遍——独立品类先红、再被大平台吸收。" | 跨域类比，给读者一个熟悉的锚点 |
| 5 | "圈外人以为 RAG 难在向量检索；圈内人都知道 80% 时间花在切分文档和处理 metadata。" | 内外视差，立刻让读者觉得"我学到了" |

### 2.2.3 五个烂的 lead 句反例

| # | 烂 lead 句 | 为什么烂 |
|---|-----------|---------|
| 1 | "在数字时代浪潮下，向量数据库迎来了爆发期。" | 套话，零信息密度 |
| 2 | "综上所述，向量数据库赛道竞争激烈。" | 空洞总结，且违反黑名单 |
| 3 | "本节将探讨向量数据库的技术架构。" | meta 句，告诉读者你要讲什么而不是直接讲 |
| 4 | "向量数据库是一种用于存储向量的数据库系统。" | 维基百科腔，定义不是判断 |
| 5 | "值得注意的是，pgvector 的崛起值得深思。" | 双重套话，且违反黑名单 |

> **自检**：把段落 lead 句单独抽出来排成一列，能否读成一份"摘要式 thesis 链"？能 = 合格。读起来像一串过渡句 = 返工。

## 2.3 事实嵌入的自然语法

### 2.3.1 规则

不要把事实写成"根据 X 报道，Y 时间，Z 公司发生了 W 事件"——这是新闻稿语法，干燥。

要把事实**揉进**叙事的因果链里，事实是叙事的**注脚**，不是叙事的**主体**。
脚注用 `<sup><a id="fact-N" class="fact-ref" href="#fact-data-N">[N]</a></sup>`。

**密度建议**：每 100-200 字一个脚注。少于这个密度叙事就飘，多于这个密度读起来像维基。

### 2.3.2 六个改写对照（烂 → 好）

```diff
1. 公司估值
✗ 烂："根据 The Information 2024-09 报道，Pinecone 的 ARR 达到了 1 亿美元。"
✓ 好："Pinecone 这一年报上来的钱在 8000 万到 1 亿美元之间转
       <sup><a id="fact-3" class="fact-ref" href="#fact-data-3">[3]</a></sup>，
       但内部的人都说这个数字注水严重。"

2. 产品发布
✗ 烂："2023 年 7 月，pgvector 发布了 0.5 版本，正式支持 HNSW 索引。"
✓ 好："pgvector 在 2023 年 7 月装上了 HNSW
       <sup><a id="fact-7" class="fact-ref" href="#fact-data-7">[7]</a></sup>——
       从那一刻开始，'专用向量库到底比 Postgres 强多少'这个问题就有答案了。"

3. 融资
✗ 烂："Pinecone 在 2023 年 4 月完成了 B 轮融资，金额 1 亿美元，估值 7.5 亿美元。"
✓ 好："2023 年 4 月那笔 1 亿美元的 B 轮
       <sup><a id="fact-2" class="fact-ref" href="#fact-data-2">[2]</a></sup>
       是这个赛道估值的天花板——之后两年都没人再喊出更高的数。"

4. 技术指标
✗ 烂："HNSW 算法的查询复杂度为 O(log N)。"
✓ 好："HNSW 把检索复杂度压到 log N 级别<sup>[12]</sup>，
       这意味着 1 亿向量和 1000 万向量的延迟差不到 3 倍——规模优势从此不再来自'数据多'。"

5. 行业事件
✗ 烂："2024 年 Q1，Supabase 在财报中将 pgvector 列为主推产品。"
✓ 好："2024 年开春 Supabase 直接把 pgvector 写进财报头条<sup>[15]</sup>——
       这是宿主把寄生品类正式收编的标志性时刻。"

6. 报告数据
✗ 烂："Gartner 报告显示，向量数据库市场规模在 2024 年达到了 12 亿美元。"
✓ 好："整个赛道的钱盘子，去年大概在 12 亿美元上下转<sup>[22]</sup>——
       小到不足以养活 5 家独角兽，大到足够让 Postgres 阵营动心。"
```

### 2.3.3 反模式：脚注堆叠

```diff
✗ 烂（脚注堆在段尾，像论文）：
"Pinecone 在 2023 年完成 B 轮融资，估值高达 7.5 亿美元，ARR 接近 5000 万美元，
团队规模约 100 人，核心客户包括 Notion、Gong 等
[1][2][3][4][5][6]。"

✓ 好（脚注随事实嵌入）：
"Pinecone 在 2023 年报出 7.5 亿估值[1]，但 ARR 才 5000 万[2]——
这意味着市场愿意按 15× revenue 给一家纯向量库定价。
今天 Notion 还在用[3]，Gong 已经悄悄迁回 pgvector[4]——
头部客户的迁出曲线，是这家公司未来 18 个月最重要的信号。"
```

## 2.4 机制段落的自然写法

### 2.4.1 规则

**机制层不写"机制层："这三个字，但保留 HTML 钩子**：

```html
<p class="mechanism" data-fact-refs="f1,f3,f5">
  机制段落的自然中文叙事
</p>
```

class 不可见，闸门能扫；`data-fact-refs` 列出本段引用的事实 id（≥3 个，由 quality_check.py 验证）。

机制段落的 lead 句不要写"它的机制是……"——而是写"为什么……"或"这件事的力学其实是……"或"内里的逻辑是……"——给读者一个**"现在我要解释一下"**的隐性信号，但不暴露分析框架。

### 2.4.2 三个完整段落示范

```html
<!-- 示范 1：飞轮型机制 -->
<p class="mechanism" data-fact-refs="f1,f3,f7">
这件事的内在引擎其实是个自我加速的循环：早期客户带来真实生产数据<sup>[1]</sup>，
真实数据训出更好的索引参数，更好的参数吸引更多客户上来——
Pinecone 在 2022-2023 这两年靠这个飞轮把单位查询成本压到了竞争对手的 1/3<sup>[3]</sup>。
但飞轮转得快有个隐藏代价：你和早期客户的耦合越来越深，
等他们规模到了想自建的时候，迁出成本反而是你帮他们降下来的<sup>[7]</sup>。

<!-- 示范 2：壁垒型机制 -->
<p class="mechanism" data-fact-refs="f4,f8,f11">
为什么向量库做不出真正的护城河？三件事卡死了：
HNSW 这类核心索引算法是公开论文<sup>[4]</sup>、
向量数据本身没有 schema 锁定（迁库脚本 200 行写完）<sup>[8]</sup>、
RAG 应用层的 SDK 都把 DB 抽象成可替换组件<sup>[11]</sup>。
三件事叠起来，结果就是"换个供应商"在这个领域是周末作业级别的工作量——
壁垒永远做不深，因为生态从设计第一天起就反对它。

<!-- 示范 3：颠覆型机制 -->
<p class="mechanism" data-fact-refs="f2,f5,f9">
pgvector 吃掉 Pinecone 的故事是经典的低端绕道：
2022 年 pgvector 还慢得没法用<sup>[2]</sup>，Pinecone 团队公开说"那玩意儿不是竞品"。
2023 年 7 月 HNSW 进 pgvector<sup>[5]</sup>，性能追到 70%。
2024 年 Supabase / Neon 等托管 Postgres 平台默认开启 pgvector<sup>[9]</sup>——
现在 80% 的 RAG 应用根本不需要单独的向量库，pgvector 够用。
Pinecone 没法降价（一降就失去 SaaS 估值），也没法补全 Postgres 的关系能力——被夹在中间。
```

每段都做到：**lead 句不暴露框架名 + 引用 ≥3 个事实 + 闭环式收尾给一个判断**。

## 2.5 观点 + 反例的自然过渡

### 2.5.1 规则

**观点 + 反例不是两段**，是**一句之内的转折**——观点写完，立刻用过渡词带出反例 / 证伪条件 / 失效场景。

HTML 形态：

```html
<blockquote class="viewpoint">
  {判断 / 预测 / 立场}
  <span class="counter">但是 / 反过来 / 如果 X 则 Y / 唯一会让这套逻辑崩的是……</span>
</blockquote>
```

`<blockquote>` 给视觉一个"这是判断"的提示（左侧引文条），`.counter` 是反例区，闸门扫这个 class 必须存在。

### 2.5.2 中文反例过渡词清单

```
但是……
反过来看……
不过要小心一件事……
这个故事的另一面是……
如果 X 越过 Y，整套逻辑就反过来跑……
唯一会让这套逻辑崩的是……
也有一种相反的解读……
悖论在于……
真正会打脸我的情况是……
```

避免："然而" / "诚然" / "辩证地看"——这些是论文腔。

### 2.5.3 三个观点 + 反例完整范例

```html
<!-- 范例 1：商业判断 + 失效条件 -->
<blockquote class="viewpoint">
  纯向量库赛道 3 年内会被压缩到 10% 的超大规模特化场景，
  剩下 90% 被 pgvector / 各家云原生 vector 服务吃掉。
  <span class="counter">但是反过来——如果 RAG 应用从"召回 top-k"演化到
  "动态多轮检索 + 强化学习排序"，那 Postgres 这种通用 DB 会重新被甩开，
  纯向量库可能凭借更激进的 ANN 算法实现迭代而起死回生。</span>
</blockquote>

<!-- 范例 2：技术判断 + 反例 -->
<blockquote class="viewpoint">
  HNSW 是当下事实标准，未来 2 年不会有挑战者。
  <span class="counter">真正会打脸我的情况是：某家硬件厂商（NVIDIA / Intel）
  推出的 ANN 加速 ASIC 让某个老算法（IVF-PQ）在硬件加速下重新有竞争力——
  这种"硬件路线翻盘软件路线"的剧本在数据库历史上演过两次。</span>
</blockquote>

<!-- 范例 3：行业范式判断 + 反共识 -->
<blockquote class="viewpoint">
  我们正处在"RAG 解决一切"的范式高潮——所有应用都在往里塞 RAG。
  <span class="counter">这个故事的另一面是：长上下文（200K+）和 KV-cache 优化
  正在让"不做检索、直接喂全文"在很多场景下变得划算——RAG 不是终局，
  RAG 可能是 2023-2025 短期最优解。</span>
</blockquote>
```

> **关键**：观点段落不是"我的判断"，是"我赌什么 + 我什么时候会被打脸"。读者读完知道你的下注，也知道你的下车信号。

# 第三部分：结构组织（v0.3 学习规律强化）

> v0.2 sample（向量数据库精研档）严格自检暴露 4 个认知规律硬伤：第 1 章缺路线图段（schemata 建构）、章节衔接 9 处不显式、第 3/4 章扁平 list 认知负荷过大、第 7 章三面镜子全在 IT 内部（同构单源化）。加上 retention 机制（self_check）和章末总结的缺失，整理出 7 条 v0.3 必加规则。每条都给"反例 → 改进"的对照，便于下次跑新领域时直接落地。

这一部分不重复第二部分已说清的内容，**只补 v0.2 没说清的 7 条新规则**。每条规则都包括：一句话规则 / 为什么（认知直觉）/ 怎么做（HTML 模板）/ 反例（v0.2 sample 实际片段）/ 检查方法。

## 3.1 第 1 章末必加路线图段（schemata 建构）

**一句话规则**：第 1 章末尾必须有 100-150 字的"接下来 9 章会怎么走"的路径预告，不是讲读完能干什么（outcome），而是讲章节之间怎么串（path）。

**为什么**：人脑读长内容前需要先建一个"挂衣架"（schema），后面的细节才有地方挂。outcome 式预告（"读完你能 X、Y、Z"）只交代终点，不交代路径——读者读到第 4 章还在猜"作者要干嘛"，认知负荷全部花在自己拼骨架上。给一段路径预告，读者把骨架接住，剩下的注意力全花在内容上。

**怎么做**（HTML 模板）：

```html
<!-- 第 1 章末尾，紧跟在"为什么现在值得花一小时"之后 -->
<blockquote class="roadmap">
  <p>接下来这九章是这样走的：
  <strong>前两章</strong>先把这个赛道的来路讲清楚——它怎么从 A 长到 B、谁在场上、各自下了什么赌注；
  <strong>中间三章</strong>翻三层——表面玩家之外的不可变约束、范式正在悄悄换班的迹象、别处的故事如何映照本地；
  <strong>后三章</strong>是收尾——主流叙事的自我强化与崩塌条件、你接下来该读谁信谁、以及我（AI）不知道的几件事。</p>
</blockquote>
```

**反例**（v0.2 sample 第 1 章实际片段）：

```html
<!-- v0.2 sample 第一章末尾 -->
<p>读完这一份你能干三件事：在投资人面前不说外行话；
在工程会议上能问对的问题；在选型会上能识别供应商的话术。</p>
```

> 这是 outcome 式预告——"读完能干什么"。读者读到第 4 章还在猜路径："为什么先讲历史再讲玩家？后面还有几章？"

**改进**（v0.3 应改成）：

```html
<p>读完这一份你能干三件事：在投资人面前不说外行话；
在工程会议上能问对的问题；在选型会上能识别供应商的话术。</p>

<blockquote class="roadmap">
  <p>接下来这九章是这样走的：第二、三章先讲来路和玩家——这个赛道是怎么从
  2017 年的 FAISS 长成 2024 年的红海、五家头部各自怕什么；
  第四到第七章翻三层——圈内黑话、不可变约束、范式拐点信号、别处的故事；
  第八到第十章收尾——主流叙事的崩塌条件、你接下来跟谁、以及我（AI）的盲区。</p>
</blockquote>
```

**检查方法**：搜 `class="roadmap"` 是否出现 1 次（且仅在第 1 章内）；段落字数 100-150 字之间；包含至少 3 个章节路径线索（如"前两章 / 中间三章 / 后三章"或"二三章 / 四到七章 / 八到十章"）。

## 3.2 每章末尾必加显式"过渡桥"

**一句话规则**：每章末（除第 10 章）必须有一段显式过渡桥，用"本章一句话定调判断 + 下一章钩子"的固定格式，不要全靠隐式过渡。

**为什么**：第 4.5 节已经说了"用一句话指向下一章"，但 v0.2 sample 实测下来 9 处衔接里只有 2 处是显式钩子，其余 7 处都是隐式过渡——读者读完一章之后注意力会自然下沉（attention dip），如果不显式拉一把，下一章的 lead 句就接不住。显式过渡桥相当于在认知断点处加一根"扶手"。

**怎么做**（HTML 模板）：

```html
<!-- 每章末尾固定加一个 transition 段，独占一段 -->
<p class="transition">
  [本章一句话定调判断]——下一章[钩子说明，给读者一个具体的悬念]。
</p>
```

格式拆解：
- 前半句：本章 thesis 的浓缩（不复述细节）
- 破折号：把判断和钩子物理性串起来（视觉断不开）
- 后半句：下一章会回答的具体问题，必须是问句或半问句

**反例**（v0.2 sample 第 5 章末尾实际片段）：

```html
<p>……所以你会发现一个吊诡的事实：
所有人都在喊"标准化"，但这个标准目前不存在。</p>
```

> 这是隐式过渡——本章自然收尾在"标准不存在"，但和下一章（第 6 章范式拐点）没有任何钩子。读者读完会停顿："然后呢？"

**改进**（v0.3 应改成）：

```html
<p>……所以你会发现一个吊诡的事实：
所有人都在喊"标准化"，但这个标准目前不存在。</p>

<p class="transition">
  五条约束告诉你这赛道为什么必须长成现在这样——但"现在"是哪个时期？
  范式正在悄悄换班吗？下一章拆开看。
</p>
```

CSS 视觉建议（在 visual-style-guide.md 落实）：`.transition { color: var(--ink-mid); font-style: italic; border-left: 2px solid var(--vermilion-faint); padding-left: 0.8em; margin: 1.5em 0; }`——视觉上比正文略弱，但比章末空白强。

**检查方法**：搜 `class="transition"` 出现次数 = 章数 - 1（第 10 章不需要）；每个 transition 段必须包含破折号 `——`；后半句必须是问号 `？` 或半问句结尾（"……下一章拆开看 / ……答案在下一段"）。

## 3.3 扁平 list 超过 5 条必须分组归类

**一句话规则**：5 条以内的同类 list 可以扁平排；6 条以上必须按维度分 3-5 组，每组前加一句 lead 提供 schema。

**为什么**：Miller's Law（7±2）说人短时记忆容量大概 5-9 项——扁平 11 条 list 已经超过容量。读者读到第 6 条就开始忘前面的，到第 11 条已经一片混沌。分组之后每组 3-4 条，每组的 lead 句给一个 chunk，读者按 chunk 记，认知负荷立即从 11 降到"4 个组 × 3 条"。

**怎么做**（HTML 模板）：

```html
<!-- 11 条圈内知识不能扁平排，分 4 组 -->
<h3>圈内人才懂的几件事</h3>

<p class="group-lead">先说<strong>工程黑话</strong>——这些词外行不会懂，但圈内人天天讲：</p>
<ul>
  <li>"召回率拉到 95% 以上 P99 就崩"——指 HNSW 在高召回区域的尾延迟</li>
  <li>……</li>
  <li>……</li>
</ul>

<p class="group-lead">然后是<strong>工程取舍</strong>——这些选择没有对错，只有适不适合场景：</p>
<ul>
  <li>……</li>
</ul>

<p class="group-lead">第三类是<strong>认知误区</strong>——多数外行（甚至部分圈内人）都搞错的事：</p>
<ul>……</ul>

<p class="group-lead">最后是<strong>圈内盲区</strong>——圈内人自己也没想清楚、但又不愿承认的事：</p>
<ul>……</ul>
```

**反例**（v0.2 sample 第 4 章实际片段，11 条扁平 list）：

```html
<h2>四、圈内人才懂的几件事</h2>
<ul>
  <li>"召回率拉到 95% 以上 P99 就崩"……</li>
  <li>"HNSW 索引重建一次得 6 小时"……</li>
  <li>"pgvector 不是真向量库"……</li>
  <li>"Pinecone 的 metadata filter 性能拉胯"……</li>
  <li>"embedding 模型一换索引全废"……</li>
  <li>"千万级以下用 pgvector 就够"……</li>
  <li>"向量库护城河 = 数据飞轮 = 谎言"……</li>
  <li>"RAG = 向量库" = 圈外人才这么说……</li>
  <li>"语义搜索能解决一切" = 销售话术……</li>
  <li>"我们用混合检索"——多数情况就是 BM25 + 向量加权……</li>
  <li>"内部其实没人真的用"——头部三家都有这个秘密……</li>
</ul>
```

> 11 条扁平排——读者读到第 6 条已经记不清前 5 条之间的差别，到第 11 条彻底失去结构感。

**改进**（v0.3 应分 4 组）：A 工程黑话（3 条）/ B 工程取舍（3 条）/ C 认知误区（3 条）/ D 圈内盲区（2 条）——每组配一句 lead 给 schema，读者按 chunk 吞。

**检查方法**：搜所有 `<ul>` 元素，`<li>` 数量 > 5 的必须在前面有 `class="group-lead"` 的段落；或者搜每章的最大 ul，超过 5 条但前面没有 lead = 返工。

## 3.4 跨领域同构禁单源——3 面镜子至少 1 面跨行业（IT 之外）

**一句话规则**：第 7 章（"别处的故事 · 镜照本地"）三面镜子（同构案例）不能全部来自同一个演化模板。强制规定：3 面镜子里必须 ≥1 面跨行业，不能全在 IT / 数据库 / 互联网内部。

**为什么**：isomorphism-lens.md 已经警告过"单源同构是廉价类比"——三面镜子全在 IT 内部，相当于用同一种基因解释三次同一件事，读者拿不到"这是普遍演化规律"还是"这只是 IT 的偶然"的判断。跨行业镜子（汽车、电力、铁路、化工、金融）能立刻把"赛道演化逻辑"从 IT 特殊性提升到产业普遍性——读者一旦看到 1910s 福特把零部件标准化的故事和 2024 年 pgvector 收编向量库的故事**结构同构**，会有"原来这是产业演化的常规剧本"的恍然大悟。这种跨域顿悟是 v0.2 sample 完全缺失的。

**怎么做**（推荐跨行业 mirror 库）：

| # | 跨行业镜子 | 同构核心 | 适用领域 |
|---|----------|---------|---------|
| 1 | 1910s 汽车零部件标准化 | 通用平台吃专用品类 | 任何"通用 vs 专用"格局 |
| 2 | 1880s 电力工业 | 独立电厂 vs 工厂自带发电机 | 任何"自建 vs 外购基础设施"赛道 |
| 3 | 1990s 金融衍生品标准化 | 场外（OTC）→ 场内（Exchange） | 任何"标准化 vs 定制化"博弈 |
| 4 | 1860s 铁路 gauge 标准化 | 多 gauge → 标准 gauge | 任何"协议碎片化→收敛"赛道 |
| 5 | 1920s 化工"单元操作"形成 | 工艺被抽象成可组合单元 | 任何"垂直整合→水平分层"演化 |

每面镜子写作时必须给"同构点"和"反同构点"——前者说"为什么这两件事在结构上一样"，后者说"哪个细节不能简单类比"。

**反例**（v0.2 sample 第 7 章三面镜子）：

```
镜 1：NoSQL 浪潮（2010s）→ 类比向量库
镜 2：Lucene/Elasticsearch（2000s）→ 类比向量库
镜 3：Memcached（2003）→ 类比向量库
```

> 三面镜子全在数据库 / 搜索引擎领域——同一个演化模板（基础设施类专用工具最终被通用平台收编）讲了三次。读者拿到的判断是"数据库圈就是这样演化的"，而不是"产业演化普遍这样"。

**改进**（v0.3 应这样配）：

```
镜 1：NoSQL 浪潮（2010s）—— IT 内部，同构最近最直接
镜 2：1880s 独立电厂 vs 工厂自带发电机 —— 跨行业，"基础设施外购化"普遍规律
镜 3：1910s 福特零部件标准化 —— 跨行业，"通用平台吃专用品类"产业普遍剧本
```

每面镜子配一段同构点 + 一段反同构点叙事化表述（不写"同构点：……" 标题，叙事化嵌入）。

**检查方法**：搜第 7 章的镜子段落（建议用 `class="mirror"` 或 `data-mirror-domain="..."` 标注），统计 `data-mirror-domain` 不在 `["it", "tech", "internet", "database", "ai"]` 的次数 ≥1；或者人工 review 三面镜子的领域归属，全在 IT = 返工。

## 3.5 玩家命门段必加"反脆弱-脆弱-杠铃-稳健"四类评分

**一句话规则**：第 3 章（"谁在场上 · 谁在赌什么"）每个核心玩家段落最后一句必须给一个结构性脆弱性判断，从 4 类标签里选一个，附一句话原因。

**为什么**：v0.2 sample 第 3 章 5 个玩家命门只讲"威胁是什么"——这只是机制层。读者拿到的是"Pinecone 的威胁是 pgvector 蚕食"，但拿不到"Pinecone 整个商业模式在结构上是反脆弱、脆弱、还是杠铃形"。后者才是 thesis-level 判断——它告诉读者"这家公司能不能扛黑天鹅"，是投资 / 选型 / 转行决策的最终输入。塔勒布的反脆弱框架在这里不是装饰，是给玩家段落补一个**结构强度评分**。

**怎么做**（4 类标签 + 模板）：

| 标签 | 含义 | 典型特征 |
|------|------|---------|
| **结构性脆弱** | 依赖单一叙事 / 估值锁定 / 单一资源依赖 | 一个故事崩了整个公司估值崩 |
| **杠铃形** | 两端暴露但有不可替代的核心 | 高风险 + 高确定性核心同时存在 |
| **反脆弱** | 寄生在更大生态上，黑天鹅强化它 | 越乱越赚，波动是养料 |
| **相对稳健** | 天花板低但抗压强 | 不容易暴富也不容易死 |

写作模板：每个玩家段落最后一句固定句式：

```html
<!-- 玩家段落末尾 -->
<p>……（前面讲玩家在赌什么、怕什么、命门在哪）。
<strong>结构判断：[标签]</strong>——[一句话原因，不超过 30 字]。</p>
```

**反例**（v0.2 sample 第 3 章实际片段）：

```html
<p><strong>Pinecone</strong>：纯向量库赌专精打通用，
最大威胁是 pgvector 在中小数据规模上的蚕食，以及 Postgres 生态的网络效应。</p>
```

> 只讲威胁（机制层），没给结构判断（thesis 层）。读者读完不知道："那 Pinecone 到底是会被慢慢蚕食死，还是黑天鹅一来就立刻崩？这是两种完全不同的脆弱性。"

**改进**（v0.3 应改成）：

```html
<p><strong>Pinecone</strong>：纯向量库赌专精打通用，
最大威胁是 pgvector 在中小数据规模上的蚕食，以及 Postgres 生态的网络效应。
<strong>结构判断：结构性脆弱</strong>——估值锁定在"纯向量库会赢"单一叙事，
叙事崩塌时无降级路径。</p>

<p><strong>pgvector / Supabase</strong>：寄生在 Postgres 生态上，
通用平台收编专用品类的产业剧本。
<strong>结构判断：反脆弱</strong>——向量库赛道越乱、Postgres 越显得稳，越赚。</p>

<p><strong>Weaviate</strong>：开源 + 多模态混合检索，赌中段市场。
<strong>结构判断：杠铃形</strong>——开源社区是不可替代的核心，
但商业化路径暴露在 SaaS 红海里。</p>
```

**检查方法**：搜第 3 章每个 `<p>` 段落里玩家名（用 `<strong>` 包的），后面必须有 `结构判断：` 字样 + 4 类标签之一；统计标签覆盖率 = 100% 才能过闸。建议在 quality_check.py 里加一条：第 3 章每个玩家段必须命中 `结构判断：(结构性脆弱|杠铃形|反脆弱|相对稳健)` 正则。

## 3.6 每章末尾加"一句话斜体总结"（retention 设计）

**一句话规则**：每章末尾（在过渡桥之前）加一段 chapter-summary，用 `<p class="chapter-summary"><em>...一句话...</em></p>`，给 thesis-level 总结，不复述细节。

**为什么**：教育心理学里 retention 曲线很陡——读者读完一章如果没有"压一下"，48 小时后能回忆起来的不到 20%。一句话斜体总结的作用不是复述（复述是冗余），而是把整章的判断**浓缩成可携带的一句话**——读者哪怕忘了所有细节，也能记住这一句。配合 3.2 的过渡桥和深研档的 self_check_questions，形成 retention 三重保险：summary 给 thesis、transition 给路径、self_check 给主动召回。

**怎么做**（HTML 模板 + 视觉规范）：

```html
<!-- 每章结构（顺序固定）：
     1. 章节正文
     2. chapter-summary（一句话斜体总结）
     3. transition（过渡桥，第 10 章除外） -->

<p class="chapter-summary">
  <em>这一章的判断只有一句：[整章 thesis 浓缩，不超过 25 字]。</em>
</p>

<p class="transition">
  [本章定调]——下一章[钩子]。
</p>
```

CSS 视觉建议：`.chapter-summary { color: var(--ink-light); font-size: 0.92em; text-align: center; margin: 2em 0 0.5em 0; letter-spacing: 0.05em; }`——视觉权重比正文低（斜体灰色 + 字号微小），不抢戏，但足以让读者在视觉上感到"一章结束了，这是浓缩"。

**反例**（v0.2 sample 第 5 章末尾，没有 chapter-summary）：

```html
<p>……所以你会发现一个吊诡的事实：
所有人都在喊"标准化"，但这个标准目前不存在。</p>
<!-- 直接进入下一章 H2，没有任何浓缩或视觉收尾 -->
```

> 读者读完 1500 字的第 5 章，没有任何"压一下"的机制——48 小时后能复述的内容大幅衰减。

**改进**（v0.3 应改成）：

```html
<p>……所以你会发现一个吊诡的事实：
所有人都在喊"标准化"，但这个标准目前不存在。</p>

<p class="chapter-summary">
  <em>这一章的判断只有一句：五条约束让向量库赛道结构上注定碎片，
  标准化是叙事不是事实。</em>
</p>

<p class="transition">
  五条约束告诉你这赛道为什么必须长成现在这样——但"现在"是哪个时期？
  范式正在悄悄换班吗？下一章拆开看。
</p>
```

**配合 retention 双保险**：深研档 sample 里必须含 `self_check_questions` 字段（≥10 道判断式）——这是主动召回（active recall）训练。chapter-summary 是被动浓缩，self_check 是主动测试，两者互补。

**检查方法**：搜 `class="chapter-summary"` 出现次数 = 章数（10）；每个 summary 段落必须包含 `<em>` 标签；字数 15-30 字之间（超过 30 字 = 在复述细节，返工）。

## 3.7 每章 lead 句必须立得住——判断式而非说明式

**一句话规则**：每章第一句必须独立成立、给出判断。不要场景式开篇（"假设你下周要去……"）作为 lead，场景钩子可以放第二句，但 lead 必须是判断。

**为什么**：第 2.2 节已经讲了 lead 句要立得住（"读者只读每段第一句能否串成 thesis 链"），但 v0.2 sample 第 1 章 lead 是场景式钩子（"假设你下周要去见 X 客户……"）——这是写小说的开法，不是写领域速通的开法。场景钩子能拉近距离，但不给判断；读者读完第一段拿到的是"作者在邀请我进入一个故事"而不是"作者已经下了一个判断"。判断式 lead 是 thesis-driven 写作的灵魂——第一句立判断，后面的事实都在为这个判断服务。

**怎么做**（推荐 lead 句类型 + 各给一个示范）：

| 类型 | 模板 | 示范 |
|------|------|------|
| **判断式** | "X 这个赛道在 Y 年悄悄做完了一件事——Z。" | "向量数据库这个赛道在 2024 年悄悄做完了一件事——算法白菜化，决胜搬到了工程和生态。" |
| **反共识式** | "你以为 X，但其实是 Y。" | "你以为向量数据库的护城河是算法，其实是数据飞轮——而这个飞轮的轴承正在松动。" |
| **历史扭曲点式** | "这个故事真正的起点不在 [近期年]，而在 [远期年] 的 [事件]。" | "这个故事真正的起点不在 2023 年的 ChatGPT 浪潮，而在 2017 年的 Facebook AI Research——FAISS 第一次把 ANN 算法工程化的那一天。" |
| **悖论式** | "X 同时是 A 和 not-A——这正是 Y 的关键。" | "向量数据库同时是基础设施又不是基础设施——这种身份分裂正是这个赛道最有意思的地方。" |

四种类型可以轮换使用——同一份速通里 10 章 lead 句不要全是同一种类型，否则节奏单调。

**反例**（v0.2 sample 第 1 章 lead）：

```html
<h2>一、这是什么 · 为什么现在值得花一小时</h2>
<p>假设你下周要去见一个准备投向量数据库赛道的投资人，
或者老板让你评估"我们要不要自建向量库"。
你打开 Google，搜出来 200 篇文章——
有讲 RAG 是终局的、有讲向量库已死的、有讲 pgvector 吊打一切的……</p>
```

> 这是场景式钩子——第一句"假设你下周要去见……"是邀请读者进入故事，但**没有任何判断**。读者读完第一段拿到的是"这是一篇会带我看清行业噪音的文章"，而不是"作者认为 X 是真的、Y 是噪音"。thesis 没刻进去。

**改进**（v0.3 应改成）：

```html
<h2>一、这是什么 · 为什么现在值得花一小时</h2>
<p>向量数据库这个赛道在 2024 年悄悄做完了一件事——
算法层已经白菜化，决胜战场搬到了工程效率和生态绑定。
所以如果你下周要去见一个准备投这个赛道的投资人，
或者老板让你评估"我们要不要自建向量库"——
你需要的不是 200 篇相互打架的博客，而是一份知道哪些信号该信、哪些该忽略的地图。</p>
```

第一句是判断（"算法白菜化，战场搬到工程和生态"），第二句才是场景钩子。判断 lead + 场景钩子的组合最稳——读者既拿到了 thesis，又拿到了带入感。

**检查方法**：抽出每章第一段第一句，连起来读——能否串成一份"摘要式 thesis 链"？这正是第 2.2 节自检清单的延续。如果 lead 句以"假设" / "想象" / "如果你" 开头 = 几乎肯定是场景式，返工。

完成一份 v0.3 领域速通后，逐条勾选下列 8 条 checklist。任意一条没勾上 = 返工。

```
[ ] 1. 第 1 章末有 roadmap 段（class="roadmap"），100-150 字，

[ ] 4. 第 7 章三面镜子（跨领域同构）至少 1 面跨行业（IT 之外）。
```

# 第四部分：领域特异性（玩家地图 / 时间叙事 / 同构 / known unknowns）

## 4.1 玩家地图叙事化

### 4.1.1 规则

**不写表格**。每个玩家一段 80-150 字的小角色刻画。

公式：

```
{X 是谁} 赌的是 {Y 路径}，
理由是 {Z 资源 / Z 时机 / Z 团队特质}，
他们最怕 {W 失效条件}。
```

5-8 个核心玩家足矣。每段独立成段，可以加 `<p class="player">` 但不强制。

### 4.1.2 三个完整玩家小段（向量数据库领域）

```html
<p><strong>Pinecone</strong> 赌的是"纯向量库 = 云原生 SaaS"——纯托管、好用 SDK、
开发者一行命令上线。理由是创始人 Edo Liberty 来自 AWS Sagemaker，
看到了"自建向量索引对应用团队太重"这个空隙<sup>[28]</sup>。
他们最怕的不是性能被追上，是 Postgres / 云厂自带的 vector 服务把"够用"做到了 80% 用户够用——
那时候单独签合同、单独走采购流程的代价就盖过了产品本身的优势。</p>

<p><strong>pgvector</strong>（Supabase / Neon / 各家托管 Postgres 阵营）
赌的是"功能下沉"——把向量列变成 Postgres 的一个 type，让 80% 的 RAG 应用
不需要单独签向量库合同。理由是 Postgres 生态过去 10 年吃掉了时序、JSON、地理数据<sup>[31]</sup>，
这次只是把剧本再演一遍。他们最怕的是"超大规模 + 严苛延迟"场景下
HNSW 的内存占用让通用 Postgres 不堪重负——但这种场景在生产环境里其实只有 5%。</p>

<p><strong>Qdrant</strong> 赌的是"Rust 性能 + 开源 + 自建优先"——给那些
"不想锁定云厂商、想自己掌控数据"的中型团队留一条退路。
理由是创始团队来自俄罗斯/欧洲，对"美国大厂掌控"有天然警惕，
正好契合欧洲合规市场的诉求<sup>[34]</sup>。
他们最怕的是被云厂商以"标准接口 + 托管版本"收编——
开源项目一旦被云巨头托管化，原始团队的商业模式就被绕过去了。</p>
```

### 4.1.3 反模式：表格化

```diff
✗ 烂（表格让玩家变成参数集）：
| 公司 | 估值 | 客户数 | 技术路线 | 创始团队 |
|------|------|--------|----------|----------|
| Pinecone | 7.5 亿 | 1000+ | HNSW | Edo Liberty |
| Qdrant | 1 亿 | 500+ | Rust + HNSW | 俄罗斯团队 |

——读者读完只记得数字，记不住格局。

✓ 好：写成 4.1.2 那种小角色刻画——读者读完能记住"Pinecone 赌什么、怕什么"，
而不是 7.5 亿这个数字。
```

## 4.2 时间叙事的三尺度交织

### 4.2.1 规则

**不切成三段（微观一段、中观一段、宏观一段）**。三个尺度像呼吸一样交织：

- **微观**：具体决策、具体事件、具体人在具体时刻说的话
- **中观**：产品演化、公司变迁、产品线之间的迁移
- **宏观**：行业周期、技术范式变迁、监管 / 资本环境变化

好的多尺度叙事**像电影运镜**：跟着主角（中观），关键节点推近到特写（微观），需要交代"为什么这件事在这个时候发生"时拉远到全景（宏观）。

### 4.2.2 250 字示范

```
2023 年 4 月，Pinecone 在那笔 1 亿美元 B 轮的发布会上
<sup><a id="fact-2" class="fact-ref" href="#fact-data-2">[2]</a></sup>，
Edo Liberty 说了一句后来被反复引用的话：
"向量库不是数据库的一个分支，是 AI 时代的核心基础设施。"
<span style="opacity:.7">——微观：一个具体场合、具体人、具体话</span>
那是 ChatGPT 上线 5 个月之后，整个赛道还在"GenAI 一切都要重做"的兴奋期里
<span style="opacity:.7">——宏观：把这一刻放在 2022.11 GenAI 拐点的语境里</span>。
但仅仅 90 天后，pgvector 0.5 装上 HNSW
<sup><a id="fact-7" class="fact-ref" href="#fact-data-7">[7]</a></sup>——
那一行 GitHub release note 没有发布会、没有融资稿、
被埋在 Hacker News 第 15 条
<span style="opacity:.7">——微观：另一个具体的小动作</span>。
之后 12 个月，Pinecone 的 ARR 增速从月环比 30% 掉到 8%
<sup><a id="fact-11" class="fact-ref" href="#fact-data-11">[11]</a></sup>，
而 Supabase 把"开箱即用 RAG"写进了核心定位
<sup><a id="fact-15" class="fact-ref" href="#fact-data-15">[15]</a></sup>
<span style="opacity:.7">——中观：两条公司演化线开始交叉</span>。
回头看，那个发布会上 Edo 那句话其实是对的——只是他没意识到，
"AI 时代的核心基础设施"未必是一家独立公司。
<span style="opacity:.7">——宏观判断收尾</span>
```

> 注释里的 `<span style="opacity:.7">` 仅仅是为了让你看清三尺度切换在哪里。**实际产出 HTML 不要写这些注释**，让段落自然流动即可。

### 4.2.3 反模式

```diff
✗ 烂（三尺度分块，机械）：

第一段（全是中观）：
"Pinecone 2021 年成立，2022 年 A 轮，2023 年 B 轮，2024 年增速放缓。"

第二段（全是微观）：
"Edo Liberty 在 2023 年的 KubeCon 上说了一段话；某工程师在 GitHub 提了一个 issue……"

第三段（全是宏观）：
"2022 年 11 月 ChatGPT 上线，开启了 GenAI 时代……"

→ 三段独立、不互相照亮、读者要自己拼。
```

## 4.3 结构层 / 范式层的叙事化

### 4.3.1 规则

**不写"reality-shaping constraint" / "硬核-保护带" / "范式时期"等学术词**。
（method-internalization 已经禁用了它们，这里给正面写法。）

**结构层叙事化模板**：

> "这个领域为什么必须长成这样？最深的 N 条约束是……"
> 然后每条约束 1 段说清——约束是什么、为什么不可压缩、如果想绕开会发生什么。

**范式层叙事化模板**：

> "我们正处在 X 范式中——核心信念是 ABC、所有人都默认 DEF。这套范式还稳，但异端已经从 Y / Z 方向浮现……"
> 然后把"硬核"翻译成"所有人默认的核心信念"，"异端"翻译成"边缘的反共识声音"。

### 4.3.2 结构层段落范例

```
向量数据库这个赛道为什么注定做不出独立护城河？最深的三条约束是：

第一，**核心算法是公开论文**。HNSW、IVF、PQ 全是学术界产物
<sup>[12]</sup>，任何一家公司想靠"我的算法更好"立壁垒，
半年内同行就能复现——这条约束是数学的，绕不开。

第二，**向量数据无 schema 锁定**。一行 1024 维 float32 数组在 Pinecone、Qdrant、
pgvector 之间的物理表达完全相同<sup>[8]</sup>，
迁库脚本 200 行写完——这条约束是数据形态的，是这个品类天然的"开放接口"宿命。

第三，**RAG 应用层的 SDK 把 DB 抽象成可替换组件**。
LangChain / LlamaIndex 从设计第一天就把 vector store 当 driver pattern 处理
<sup>[11]</sup>——这条约束是生态的，是这个领域的应用层主动反对了底层锁定。

三条约束叠起来，结论几乎是数学的：**这个赛道不会出现独立的、估值百亿的玩家**。
能赚钱的位置在两端——上端是把 RAG 嵌进存量业务的老牌厂商，下端是把 vector
做成 Postgres 列类型的通用 DB——中间这一层永远做不深。
```

### 4.3.3 范式层段落范例

```
我们目前正处在"RAG 是通用解"的范式高潮——所有 LLM 应用默认要做检索增强、
所有产品 demo 都要展示"接入你的数据"。这套范式的核心信念是
**长上下文太贵 + 模型不能动态学习 + 私有数据必须在边缘**——
这三个假设撑着整个 RAG 工具链的存在合理性。

但异端已经从两个方向浮现：

一是**长上下文路线**——Gemini 的 1M context、Claude 的 200K context
让"小一点的私有库直接全部喂进去"在很多场景下成本可接受
<sup>[19]</sup>。
当全文喂进去比 chunk + 检索更准、延迟也能接受时，RAG 链路第一段（检索）就被绕开了。

二是**模型内置记忆路线**——OpenAI 的 Memory、Anthropic 的 Projects
开始在模型层面做用户级记忆<sup>[24]</sup>。
当 LLM 自己记得"上一次对话"和"用户的常用文件"时，
应用层那一整套 RAG 编排就重叠了。

这两条异端目前还都在边缘——因为代价（context 成本、记忆质量）还没追上。
但 2025-2026 之间是关键观察期：如果 token 成本再降一个数量级、
模型记忆质量再提一档，"RAG 必须做"这个范式假设就会松动。
那时候整个向量库赛道的存在合理性都要重新审视——而不只是某一家公司的定位。
```

## 4.4 跨领域同构的"故事化"

### 4.4.1 规则

**不写"同构点 / 反同构点"**这两个词（method-internalization 黑名单）。

写："这一切其实在 X 领域 Y 年前演过一遍——相似的是 ABC……差异在 DEF……所以参考 X 的剧本只能参考一半。"

**关键**：相似 + 差异要**同样讲清楚**——只讲相似 = 滥用类比，只讲差异 = 类比无效。

### 4.4.2 200 字完整案例

```
向量数据库的故事，其实在 2010 年代的 NoSQL 赛道演过一遍。

相似的部分：
当年 MongoDB / Cassandra / Couchbase 也是一波"通用 DB 解决不了我们的问题"的新品类创业潮，
2012-2015 估值飞涨、独角兽迭出。然后 PostgreSQL 在 2014-2018 之间靠 JSONB
吃掉了 60% 的"我需要文档存储"场景<sup><a id="fact-40" class="fact-ref" href="#fact-data-40">[40]</a></sup>，
独立 NoSQL 公司估值集体回调——MongoDB 上市后股价跑赢但靠的是 Atlas 云服务，
不再是 NoSQL 这个品类本身。今天 pgvector 之于 Pinecone，
几乎是 PostgreSQL JSONB 之于 MongoDB 的复刻。

差异的部分：
但有一处差异不能忽略——**向量检索的算法门槛比 JSON 解析高得多**，
HNSW 在 1B+ 规模下的内存优化是真有 know-how 的<sup>[13]</sup>，
而 JSONB 本质上是文本解析。所以"超大规模特化场景"在向量库这边可能比 NoSQL 那边
更能撑出一块独立生存空间。结论：剧本相似到 70%，但终局可能不是"全军覆没"，
而是"压缩到 10-15% 的超大规模 + 严延迟场景，剩下都被通用 DB 收编"——
这就是相似只到一半的意思。
```

> **检验**：读完这一段，读者应该既知道"哪里能借鉴当年 NoSQL 的剧本"，
> 也知道"哪里不能照搬"。两件事缺一就是单边类比。

## 4.5 Known Unknowns 第一人称

### 4.5.1 规则

**用第一人称承认 AI 视角的局限**——不要装客观。
"我（AI）不知道……" / "我训练数据里没出现……" / "我的 cutoff 之后这件事的发展我不掌握……"

为什么这样？因为读者读到这一段时，会潜意识把作者当成"懂行的朋友"——朋友可以说"这件事我不确定"，但分析报告说"存在不确定性"读起来就是塑料感。

### 4.5.2 三条范例 known unknowns（向量库领域）

```html
<ol>
<li>我不知道 Pinecone 的真实 ARR——The Information 2024-09 报道了一个 1 亿美元的数字<sup>[3]</sup>，
但这个数字的口径（ARR vs revenue vs bookings）我没法确认。
内部人对这个数字的诚实度也有不同声音，我没有渠道交叉验证。</li>
<li>我不确定中国市场的格局——Zilliz / Milvus 在国内的客户分布、与阿里云 / 百度云的竞合
关系、信创合规对纯向量库的影响，公开材料质量参差，且大多带宣传色彩。
本份速通对中国市场的描述只到"知道存在 Milvus 这家"为止，再往下需要本地 insider。</li>
<li>我没法判断"长上下文 + KV cache 优化"的成本下降速度——这件事直接决定 RAG 范式
能维持多久，但这是 2024 年下半年到现在最快变化的领域，
我的 cutoff 之后的最新算法和定价我不掌握。</li>
</ol>
```

> 这一段的语气和前面的章节应该是连续的——你刚刚才用一个能干的朋友的口吻给读者讲完故事，
> 这一章继续用这个朋友的口吻说"但是有几件事我也没把握"。

## 4.6 章节衔接的自然过渡

### 4.6.1 规则

**章节末尾用一句话指向下一章**，不要让 10 章独立成岛。

不要写"接下来我们将探讨……" / "下一节将……"——这是 meta 句。
要写"这就把我们带到下一个问题：……" / "但要理解这一切，得先看……" / "这件事到底为什么没崩？答案在下一段……"

**关键**：过渡句应该是**当前章节的逻辑收尾**，同时**埋下一章的钩子**。

> 注：这一节给"自然过渡"的最低要求；第 3.2 节给的是 v0.3 升级版"显式过渡桥"。两者不冲突——3.2 是 4.6 的强化形式（每章末加 `class="transition"` 段，含破折号 + 问号收尾）。

### 4.6.2 三个章节衔接范例

```html
<!-- 范例 1：从"它怎么走到今天"到"谁在场上" -->
<!-- 第二章末尾 -->
<p>……到了 2024 年中，这个赛道已经有了清晰的几股力量——
他们各自下的赌注非常不同，怕的事情也非常不同。
</p>
<!-- 然后第三章 H2 接着写 -->

<!-- 范例 2：从"圈内人才懂的几件事"到"表面之下 · 不可变的约束" -->
<!-- 第四章末尾 -->
<p>……这些黑话和盲区背后，其实指向一件更深的事：
为什么这个赛道注定长成现在这个样子？
往下挖三层，会看到几条不可压缩的约束——它们解释了为什么前面所有现象不可能不是这样。
</p>

<!-- 范例 3：从"主流叙事"到"接下来读什么" -->
<!-- 第八章末尾 -->
<p>……所以如果你听到"RAG 是终局"这种叙事，
要在心里默默 mark 一下"如果 X 信号出现，这个故事就崩"。
但读到这里，你大概也想知道——
**如果我想再深一层、想跟谁、想加入哪个圈子？** 答案在最后一节。
</p>
```

> 三档输出都应该用同一套过渡句——闪研档把过渡句删一半也读得通，
> 但精研 / 深研档的过渡句让 10 章像一个连续故事。

## 4.7 末尾自检清单（写完一份领域速通后自问）

写完一份完整的 HTML 之后、上闸门之前，**逐条问自己 7 个问题**。
任意一条答"不"，回去返工。

```
[ ] 1. 整份 HTML 没有 H2 / H3 出现"事实层 / 机制层 / 观点层 / 反身性 /
       结构层 / 范式层 / 跨域同构 / 骨架·一二三四五"这些词。

[ ] 2. 读者只读每段第一句，能否串成一份"摘要式 thesis 链"？
       不能 = lead 句没立住，返工。

[ ] 3. 读者能否用一句话向第三方复述 thesis？
       "我刚读了一份 XX 速通，作者的核心判断是 Y。"
       说不出 = thesis 没刻进文章里。

[ ] 4. 每个观点段落是否都暗藏反例 / 证伪条件？
       搜索 `class="counter"`，每个 viewpoint 段落必须命中一次。

[ ] 5. 每段事实脚注密度合理吗（每 100-200 字 1 个）？
       密度过低 = 飘；密度过高 = 维基。

[ ] 6. 三尺度时间叙事是否自然交织？
       搜整个第二章（领域速通的"它怎么走到今天"那一章），
       看微观 / 中观 / 宏观是否在 250 字内都出现过。

[ ] 7. Known Unknowns 是否用第一人称写？
       搜"我（AI）不知道" / "我训练数据里没出现" / "我的 cutoff"——
       至少出现 3 次。装客观 = 失败。
```

> 这一条 7 项 + 第三部分的 8 项 + 第一部分语言宪法的 5 问 + grep 三道扫描 = 完整自检矩阵。

## 附录：v0.2 写作的"最小阻力路径"

如果你只能记住三件事：

1. **先想骨架，再想叙事**——脑子里跑完事件 / 机制 / 结构 / 范式 / 反身性 / 同构这套
   分析，然后**把分析名字全部丢掉**，只把判断和事实组织成段落。

2. **每段开头是判断，不是过渡**——lead 句单独抽出来要能成立。

3. **观点必带反例，事实必嵌叙事**——单边判断 = 单边叙事 = AI Slop；
   干燥事实 = 维基百科腔。两边都不要。

写到这里你已经掌握了 v0.2 的全部要义。剩下的是练习——在向量库 / REITs /
日本动画 / World Model 这些不同领域里反复跑这套规范，每跑一次都自检三套清单
（语言宪法 5 问 + v0.2 自检 7 条 + v0.3 自检 8 条），直到这套规范变成肌肉记忆。
